# 보행 로봇 — 절차적 애니메이션 + 물리

애니메이션 클립 없이 **계산만으로** 걷습니다. 애니메이터도, 걸음 주기 시계도 없습니다.
발이 제자리에서 밀려나면 걸음이 시작되고, 몸통은 발들이 만드는 평면을 늦게 따라갑니다.

**다리 수를 가리지 않습니다.** 2족 · 3족 · 4족 · 6족이 전부 같은 코드로 걷습니다.

## 세 가지 템플릿

메뉴 `CarDrive > Gameplay > 보행 로봇 > 전부 만들기`
(하나씩 만들려면 그 아래 1 · 2 · 3 항목)

| | 4족 보행기 | 2족 드레드노트 | 3족 스트라이더 |
|---|---|---|---|
| 흉내 낸 것 | 기초 4족 로봇 | 워해머 40K 드레드노트 | 하프라이프 2 스트라이더 |
| 다리 | 4 | 2 | 3 |
| 관절이 꺾이는 쪽 | 바깥 위 (벌어짐) | **뒤 (역관절)** | 바깥 위, 아주 높이 |
| 몸통 높이 | 0.42m | 2.2m | **5.2m** |
| 질량 | 320kg | 900kg | 2000kg |
| 걸음 | 교대보 (대각선) | 교대보 (좌우) | **파도보** (한 발씩) |
| 다리 뻗기 | 0.84m | 3.4m | 7.8m |
| 작업 반경 | 0.49m | 1.53m | 3.34m |
| 걸음 하나 | 0.22초 | **0.55초** (쿵) | 0.58초 |
| 순항 / 한계 | 1.6 / 3.46 m/s | 1.4 / 3.06 m/s | 2.2 / 6.34 m/s |

셋은 보행 로봇 설계 공간에서 서로 가장 먼 세 점입니다. 셋이 같은 코드로 걸으면 그 사이의 어떤 것도 됩니다.

- **2족**은 한 발을 들면 지지점이 하나가 되어 몸이 **버티는 발 위로 쏠립니다.** 따로 만든 연출이 아니라 발 평균에서 저절로 나옵니다.
- **3족**은 다리가 홀수라 절반으로 나눌 수 없습니다. 그래서 파도보만 가능하고, 항상 두 발이 남아 넘어지지 않습니다.
- **역관절**은 벡터 하나(`kneePole = 뒤쪽`)가 전부입니다. 앞으로 바꾸면 같은 리그가 곧바로 사람처럼 보입니다.

## 물리

리지드바디 · 몸통 콜라이더 · `RobotPhysicsMotor` 셋이 붙어 있습니다. 그래서 로봇은

1. **부딪힙니다** — 바위·나무·차량을 통과하지 못합니다
2. **밀립니다** — `motor.AddImpulse(충격량)` 으로 날아갑니다
3. **떨어집니다** — 발이 닿을 땅이 없으면 중력이 데려갑니다
4. **눌립니다** — 다리가 몸을 떠받치는 힘이 용수철이라 착지 충격에 살짝 주저앉았다 펴집니다
5. **휘청입니다** — 얻어맞으면 몸통이 맞은 쪽으로 젖혀졌다가 몇 번 흔들리며 돌아옵니다
6. **넘어지고 일어납니다** — 세게 받히면 자빠져 구르고, 멈추면 스스로 몸을 세웁니다

### 매 물리 프레임에 걸리는 힘 넷

전부 `ForceMode.Acceleration` 입니다. 질량과 무관하게 같은 반응을 내고, 질량은 **밀렸을 때 얼마나 버티는가**에만 쓰입니다.

| | 하는 일 | 식 |
|---|---|---|
| **지지** `ApplySupport` | 발 높이로 몸을 끌어올림 + 중력 상쇄 | `(발높이 − 몸높이)·k − 수직속도·c − 중력` |
| **이동** `ApplyMove` | 목표 속도로 다가감 | `(목표속도 − 현재속도)·제어세기` |
| **회전** `ApplyTurn` | 목표 회전 속도로 다가감 | `(목표각속도 − 현재각속도)·제어세기` |
| **상한** `ClampSpeed` | 밀려나는 속도를 자름 | 수평 속도를 `maxPushSpeed` 로 |

- **지지**는 오차 0에서 중력이 정확히 상쇄되므로 평지에서 가라앉지 않습니다. 강성 60 · 감쇠 12 는 임계값(2√60≈15.5)보다 낮아 **살짝 언더댐프** — 착지할 때 한 번 눌렸다 펴집니다.
- **이동**은 1차 시스템이라 시정수가 `1/제어세기` ≈ 83ms 입니다. 그래서 밀리면 곧바로 제자리로 튀지 않고 **밀린 티가 납니다.**
- **회전**은 X·Z 축이 `FreezeRotation` 이라 **루트는 절대 넘어지지 않습니다.** 기우는 것은 언제나 몸통(자식)이고, 그래야 발 평면에서 뽑은 기울기와 두 번 겹치지 않습니다.
- 다리에는 콜라이더가 없습니다. 다리는 계산으로 움직이므로 물리로 밀 대상이 아니고, 있으면 **발이 자기 다리를 밟습니다.**

### 휘청임은 왜 따로 필요했는가

리지드바디를 밀면 몸이 **꼿꼿한 채로 옮겨 갑니다.** 실제로 맞은 것은 몸통인데 자세가 그대로면 밀려난 것이지 맞은 것으로 보이지 않습니다.
그래서 `WalkerRobot.AddImpact` 가 몸통 기울임을 **따로** 흔듭니다.

```
충격 속도 → 앞뒤·좌우 성분 → 기울기(도) → 2차 시스템의 속도를 때림 → 몇 번 넘나들다 0으로
```

**기울어지는 방향은 미는 쪽과 반대입니다.** 스스로 가속할 때는 다리가 땅을 밀어 몸이 진행 방향으로 숙이지만(`pitchIntoAccel`),
밖에서 맞으면 발은 그 자리에 있고 몸통만 밀려나므로 **맞은 쪽으로 젖혀집니다.** 두 기울임의 부호가 반대인 이유입니다.

기울기의 크기는 `impactTiltPerSpeed`(1m/s 당 몇 도)로 **직접** 정합니다. 2차 시스템을 때리면 각도가 곧바로 그만큼 되는 게 아니라
어느 지점에서 가장 크게 벌어졌다 돌아오므로, 그 최댓값이 원하는 값이 되도록 `SecondOrderDynamics.ImpulseForPeak` 이 변환합니다.
덕분에 **용수철을 느리게 바꿔도 기울기는 그대로이고 흔들리는 시간만 길어집니다.**

| | 진동수 / 감쇠 | 5m/s 로 맞았을 때 | 잦아드는 시간 |
|---|---|---|---|
| 4족 보행기 | 2.4 / 0.35 | 14° | 0.5초 (탁 흔들리고 끝) |
| 2족 드레드노트 | 1.3 / 0.25 | 12° | 1.1초 (묵직하게 두어 번) |
| 3족 스트라이더 | 0.9 / 0.22 | 10° | 2.0초 (아주 느린 흔들림) |

### 충돌 판정은 상대 속도가 아니라 충격량

`OnCollisionEnter` 에서 보는 값은 `collision.impulse / 질량` — 그 충돌이 만든 **속도 변화**입니다.
상대 속도로 재면 조약돌이 빠르게 스쳐도 2톤짜리가 휘청이고, 무거운 차가 천천히 밀면 아무 일도 없습니다.
충격량으로 재면 **상대의 무게가 저절로 셈에 들어갑니다.**

배선은 필요 없습니다. 어떤 리지드바디든 세게 부딪히면 휘청이고, 더 세면 넘어집니다.
코드에서는 `motor.AddImpulse(충격량)` 하나로 **밀림과 휘청임이 함께** 걸립니다.

그리고 밀려나면 발이 작업 반경 밖으로 나가므로 `RescueStretchedLeg` 가 보행 규칙을 어기고 발을 뗍니다 —
**비틀거리며 발을 다시 딛는 모습**은 따로 만든 것이 아니라 여기서 나옵니다.

## 넘어지고 일어나기

```
서 있음 ──(충격이 문턱을 넘음)──▶ 쓰러짐 ──(멈춤)──▶ 누움 ──(뜸)──▶ 일어남 ──▶ 서 있음
                                  물리          판정        대기       계산
```

**넘어지는 것은 물리에 맡깁니다.** 루트의 회전 잠금(`FreezeRotationX|Z`)을 풀고 넘어뜨리는 회전 충격을
한 번 준 뒤, 힘을 전부 끊고 손을 뗍니다. 그러면 몸통 상자가 지형과 부딪히며 **스스로 구르고 멈춥니다.**
넘어지는 자세를 미리 만들 필요가 없고, 비탈에서는 굴러 내려가기까지 합니다.

넘어뜨리는 축은 **미는 방향과 수직인 수평축**입니다. 그 축으로 돌려야 밀린 쪽으로 자빠집니다.

**일어나는 것은 계산으로 합니다.** 물리로 일으켜 세우려면 관절 토크와 균형 제어기가 필요합니다.
대신 리지드바디를 잠시 **기구학 모드**로 바꿔 자세와 높이를 정해진 시간에 걸쳐 되돌립니다.
다 서면 물리로 돌려줍니다.

### 일어나는 안무 — 다리가 먼저, 몸이 나중

```
4족 보행기 (1.3초)
  다리0  0.00 -> 0.43s  |========
  다리1  0.10 -> 0.52s  | ========
  다리2  0.19 -> 0.62s  |   ========
  다리3  0.29 -> 0.72s  |     ========
  몸통   0.45 -> 1.30s  |         ################
```

발은 **평소의 걸음과 똑같은 호**를 그리며 옮겨집니다. 다리마다 출발 시각을 어긋나게 두어
**하나씩 차례로 딛고**, 그 위로 몸이 뒤따라 올라옵니다.

#### 어디서 조정하는가

| 값 | 붙어 있는 곳 | 하는 일 |
|---|---|---|
| `riseDuration` | `RobotKnockdown` | 일어나는 데 걸리는 **전체 시간** |
| `riseLegFraction` | `RobotKnockdown` | 그중 **다리를 옮기는 데** 쓰는 비율 |
| `riseBodyDelay` | `RobotKnockdown` | **몸이 올라오기 시작하는** 시점 |
| `riseOrder` | `WalkerRobot` | 다리를 딛는 **차례** |
| `riseStepShare` | `WalkerRobot` | 한 다리가 차지하는 시간 비율 = **겹치는 정도** |
| `riseLiftScale` | `WalkerRobot` | 발이 그리는 호의 높이 |

시각은 `WalkerRobot.BeginRise` 가 이렇게 계산합니다.

```
다리 구간   = riseDuration × riseLegFraction
한 걸음     = 다리 구간 × riseStepShare
간격        = (다리 구간 − 한 걸음) ÷ (차례 수 − 1)
i번 출발    = 간격 × (i번 다리의 차례)
```

**차례(`riseOrder`)는 셋 중에 고릅니다.** 같은 차례를 받은 다리는 함께 나갑니다.

| | 4족에서 (전체 1.3초 기준) |
|---|---|
| `LegOrder` (기본) | FL → FR → BL → BR, 0.10초 간격으로 하나씩 |
| `GaitGroups` | {FL, BR} → {FR, BL}, **걸을 때와 같은 대각선 짝**으로 둘씩 |
| `LowestFirst` | **땅에 가까운 발부터**. 옆으로 누우면 아래쪽 다리가 먼저 몸을 받칩니다 |

**`riseStepShare` 가 차례를 얼마나 뚜렷하게 보여 줄지**를 정합니다.
1이면 간격이 0이 되어 **네 다리가 동시에** 나가고, 0.3이면 하나가 거의 끝난 뒤 다음이 출발해 또박또박 보입니다.

```
share 1.0 (동시)        share 0.6 (기본)         share 0.3 (또박또박)
FL |=================   FL |==========           FL |=====
FR |=================   FR |  ==========         FR |    =====
BL |=================   BL |    ==========       BL |        =====
BR |=================   BR |       ==========    BR |            =====
```

몸통은 그동안 *루트를 따라가는 자세*에서 *발에서 뽑은 자세*로 서서히 넘어갑니다.
둘 중 하나만 쓰면 어색합니다 — 발에서만 뽑으면 아직 공중에 있는 발 때문에 몸이 엉뚱한 데 가고,
루트만 따르면 발이 땅을 딛는데도 몸이 그것을 모른 척합니다.

> **왜 예전에는 순간이동처럼 보였는가.** 원인이 셋이었습니다.
> 1. 매 프레임 **루트 기준 제자리**를 목표로 삼았습니다. 그런데 일어나는 동안 루트가 눕힌 자세에서 선 자세로 돌아가므로 그 제자리가 **거대한 호를 그리며 쓸려 다녔고**, 발은 그것을 쫓다가 끌려가듯 미끄러졌습니다.
> 2. 다 선 순간 `PlantAllFeet()` 로 **네 발을 한꺼번에 스냅**했습니다. 마지막 프레임의 순간이동이 여기서 나왔습니다.
> 3. 쓰러지는 순간에도 다리가 **한 번에** 늘어졌습니다.
>
> 지금은 다 섰을 때의 발자리를 **미리 계산해 세계에 고정**하고, 늘어지는 것도 시간을 두고 풀립니다.

> **왜 나눴는가.** 넘어지는 순간은 *예측할 수 없어야* 재미있고(어디로 구를지 모름),
> 일어나는 순간은 *예측할 수 있어야* 합니다(언제 다시 위협이 되는지 알아야 함).
> 물리와 계산의 경계를 그 두 성질에 맞춰 그었습니다.

쓰러진 동안 다리는 **관절이 풀린 것처럼 처집니다**(`limpSag`). 발을 세계에 고정해 두면
구르는 몸에 발만 박혀 다리가 고무줄처럼 늘어나므로, 다리가 붙은 자리에서 중력 쪽으로 처지게 둡니다.
일어날 때는 걸음 규칙을 멈추고 발을 제자리로 **모읍니다** — 안 그러면 "발이 제자리에서 멀다"는 이유로
네 다리가 한꺼번에 걸음을 시작해 버립니다.

| | 넘어지는 문턱 | 누워 있는 시간 | 일어나는 시간 |
|---|---|---|---|
| 4족 보행기 (320kg) | 3.5 m/s | 0.6초 | 1.3초 |
| 2족 드레드노트 (900kg) | 5.0 m/s | 1.0초 | 2.2초 |
| 3족 스트라이더 (2000kg) | **7.0 m/s** | 1.6초 | **3.5초** |

밖에서 부를 수도 있습니다.

```csharp
knockdown.Knockdown(방향, 세기);   // 스크립트로 자빠뜨리기
knockdown.StandUpNow();            // 지금 일으키기
knockdown.riseAutomatically = false;   // 쓰러진 채로 두기
if (knockdown.IsDown) { ... }      // 지금 못 싸우는 상태인가
```

`RobotKnockdown` 을 떼면 넘어지지 않고 휘청이기만 합니다. 물리 모터의 `Struck` 사건에
소리·피해를 함께 걸 수도 있습니다.

## 때려 보기 — 디버그 발사기

메뉴 `CarDrive > Gameplay > 디버그 발사기 배선` 을 누르면 플레이어의 조준 기준(카메라)에
`DebugProjectileLauncher` 가 붙습니다. 실행하고 **F** 를 누르면 조준한 방향으로 리지드바디 공이 날아갑니다.

**맞은 쪽이 받는 속도 변화**는 한 줄로 정해집니다.

```
Δv ≈ (발사체 질량 × 속도) ÷ (맞은 것의 질량 + 발사체 질량)
```

분모에 발사체 질량을 더하는 이유는 **공이 벽처럼 멈춰 서지 않기 때문**입니다.
부딪힌 뒤 둘이 운동량을 나눠 가지므로 맞은 쪽이 전부 받지는 못합니다.

기본값 60kg × 40m/s = **2400 N·s** 로 쐈을 때:

| 대상 | 받는 Δv | 넘어짐 문턱 | 결과 |
|---|---|---|---|
| 4족 보행기 (320kg) | 6.3 m/s | 3.5 | **넘어짐** |
| 2족 드레드노트 (900kg) | 2.5 m/s | 5.0 | 휘청임 |
| 3족 스트라이더 (2000kg) | 1.2 m/s | 7.0 | 살짝 휘청임 |

무거운 쪽을 넘어뜨리려면 인스펙터에서 `mass` 나 `speed` 를 올리면 됩니다.
(스트라이더는 Δv 7 이 필요하니 예를 들어 400kg 을 42m/s 로)
쏠 때마다 운동량이 로그에 찍히므로 계산할 필요는 없습니다.

> **연속 충돌 검사를 켜 둡니다.** 40m/s 짜리 공은 60fps 에서 한 프레임에 0.67m 를 갑니다.
> 로봇의 몸통 상자는 그보다 얇아서, 기본 검사로는 **그냥 통과해 버립니다.**

키는 `GameInput.GetDebugKeyDown` 으로 읽습니다. 게이트를 지키므로 오버레이가 떠 있으면 발사되지 않고,
그렇다고 키 배치 화면에 정식 기능처럼 나타나지도 않습니다.

### 다리는 어디까지 물리인가

다리에도 물리가 있습니다. 다만 **세 수준 중 두 번째**까지입니다.

| | 넣었나 | 얻는 것 |
|---|---|---|
| ① 마디마다 **기구학** 리지드바디 + 캡슐 콜라이더 | ✅ | 걸어가며 통을 걷어차고, 넘어질 때 다리가 지형에 걸립니다 |
| ② 통제 상실 시 **Verlet 진자** | ✅ | 힘이 풀린 다리가 관성으로 휘둘리고 땅에 닿아 멈춥니다 |
| ③ 마디마다 **조인트**를 건 완전 래그돌 | ❌ | 다리끼리 엉키고, 다리 무게가 구르는 방향을 바꿉니다 |

**①이 왜 기구학인가.** 콜라이더만 붙이면 유니티는 그것을 *정적 콜라이더*로 봅니다.
정적 콜라이더를 매 프레임 옮기면 공간 분할을 통째로 다시 만들고, 그러고도 부딪힌 쪽에 힘을 주지 못합니다.
움직이는 콜라이더에는 **반드시 리지드바디가 있어야** 합니다.
기구학으로 두면 **다리가 세계를 밀되 세계가 다리를 밀지는 못합니다** — 다리 각도는 IK 가 정해야 하니까요.

> 다리 콜라이더는 **몸통과 다른 리지드바디**이므로, 걸어가며 땅에 닿아도
> 몸통의 `OnCollisionEnter` 가 불리지 않습니다. 걸을 때마다 휘청이지 않는 이유입니다.

#### 자기 몸끼리의 충돌 — 가리지 말고 고치기

처음에는 `Physics.IgnoreCollision` 으로 **자기 콜라이더 쌍을 전부** 껐습니다.
그러지 않으면 로봇이 제자리에서 덜덜 떨었기 때문입니다. 그런데 그것은 원인을 고친 것이 아니라
**겹친 모양을 가린 것**이었습니다. 재 보니 세 리그 모두 <b>고관절 구체가 몸통 상자 안에 박혀</b> 있었습니다.

| | 고치기 전 | 고친 뒤 (정지) | 25·22·18도 기울여도 |
|---|---|---|---|
| 4족 보행기 | **−0.055 m** | +0.050 m | +0.049 m |
| 2족 드레드노트 | **−0.021 m** | +0.229 m | +0.147 m |
| 3족 스트라이더 | **−0.117 m** | +0.083 m | +0.060 m |

고관절을 몸통 상자 **밖으로** 뺐습니다 — 4족은 옆으로(0.26→0.40), 2족은 아래로(−0.70→−1.15),
3족은 옆·뒤로(0.45→0.85, −0.90→−1.50). 빈 틈은 **받침대**가 메웁니다.
받침대는 장식이라 콜라이더가 없습니다 — 몸통의 충돌 모양을 상자 하나로 두어야 여유를 계산대로 보장할 수 있습니다.

> **기울임까지 확인해야 했습니다.** 다리는 몸통의 자식이라 몸이 기울면 함께 휩쓸리는데,
> 몸통 콜라이더는 루트에 고정되어 있습니다. 처음 잡은 값은 서 있을 때는 멀쩡했지만
> 드레드노트가 22도 기울자 **−0.053m 파고들었습니다.** 정지 자세만 보고 넘어갔으면 놓쳤을 문제입니다.

이제 무시하는 것은 **같은 다리 안의 마디끼리**뿐입니다. 넓적마디와 종아리마디는 관절에서 언제나
맞닿아 있어 구조적으로 겹치는 것이고, 그건 끄는 것이 맞습니다.
**다리 ↔ 몸통과 다리 ↔ 다른 다리는 살아 있습니다.**

덤으로 다리가 더 수직에 가까워지면서 **작업 반경이 30~90% 늘었습니다.**
(4족 0.37→0.49m) 보폭이 커지고 낼 수 있는 속도도 함께 올랐습니다.

**솔직한 한계 하나.** 다리가 기구학이라 PhysX 는 **다리 ↔ 다리 쌍을 풀지 않습니다**
(기구학끼리는 충돌을 해결하지 않습니다). 그래서 "다리끼리 엉키는" 그림은 아직 나오지 않습니다.
지금 살아난 것은 **다리 ↔ 몸통**이고, 쓰러진 로봇의 다리가 몸을 받치는 움직임이 여기서 나옵니다.
다리끼리 엉키게 하려면 다리를 동적 리지드바디로 바꾸고 조인트를 걸어야 합니다(③).

리그를 손으로 고쳐 겹치게 되었다면 `WalkerRobot.selfCollision` 을 끄면 예전처럼 전부 무시합니다.

**②가 통제 상실입니다.** 쓰러지면 발이 더 이상 IK 목표를 따라가지 않고
**붙은 자리에 매달린 추**가 됩니다. 점 둘짜리 `VerletChain` — 다리가 붙은 자리(고정)와 발 —
이고, 거리 제약이 둘을 이어 주므로 단단한 막대에 매달린 추처럼 굽니다.
몸이 구르면 발이 관성으로 뒤따라 휘둘리고, 땅에 닿으면 그 자리에서 멈춥니다.

예전에는 발을 목표 자세로 **선형 보간**했습니다. 그건 "늘어진 것처럼 보이게 그린 것"이지
늘어진 것이 아니어서, 몸이 아무리 굴러도 다리가 같은 모양을 유지했습니다.

**③을 왜 뺐는가.** 얻는 것보다 잃는 것이 큽니다.
- 마디 12개(4족)에 조인트 12개를 걸고 각각 튜닝해야 합니다. 잘못 잡으면 떨거나 폭발합니다.
- 어려운 것은 넘어지는 쪽이 아니라 **돌아오는 쪽**입니다. 물리가 만든 자세에서 IK 자세로
  블렌딩해야 하는데, 이 시스템에는 이미 **의도적으로 짜 놓은 기립 안무**가 있습니다. 그것과 충돌합니다.
- 이 구조의 전제가 "걸음은 계산, 물리는 몸" 이었습니다. ③은 그 전제를 뒤집습니다.

필요해지면 `WalkerLeg` 에 조인트 모드를 얹는 것은 가능합니다. 지금 구조가 그것을 막지는 않습니다.

몸을 떠받치는 것은 `WalkerRobot.SupportHeight`(발들이 딛고 있는 높이)로 끌어올리는 **용수철 + 감쇠**입니다.
자동차 서스펜션과 같은 구조이고, 중력을 상쇄해 두어 평지에서는 가라앉지 않습니다.
발밑이 `fallThreshold` 보다 깊으면 용수철을 끊습니다 — 그러지 않으면 낭떠러지에서 **떨어지는 게 아니라 빨려 들어갑니다.**

물리가 필요 없으면 `RobotPhysicsMotor` 만 떼면 됩니다. 드라이버가 트랜스폼을 직접 옮기는 예전 방식으로 돌아갑니다.

## 어떻게 움직이는가 — 목표 위치

이동 명령이 아니라 **목표 위치**로 걸어갑니다.

```
실행 → 씬 뷰에서 "..._Destination" 마커를 끌어 옮김 → 로봇이 그리로 걸어감
```

코드에서는 `RobotDriver.SetDestination(worldPosition)`. `destinationTarget` 에 아무 트랜스폼이나 꽂아도 됩니다.

**왜 명령이 아니라 목표인가.** 키 입력을 그대로 속도로 바꾸면 다리가 따라올 수 있는지와 무관하게 몸이 나아갑니다.
목표로 바꾸면 얼마나 빨리 갈지를 드라이버가 정할 수 있고, `WalkerRobot.MaxTravelSpeed` 로 **다리가 감당하는 속도**에 묶을 수 있습니다.

## 걸음이 끊기지 않는 이유 — 다리 기하가 박자를 정합니다

발은 제자리에서 **작업 반경** 안에서만 놓일 수 있습니다. 벗어나면 IK 가 한계에서 잘려 다리가 뻗은 채 미끄러집니다.
그래서 모든 수치를 이 반경에서 거꾸로 뽑습니다.

```
작업 반경 = √(뻗을 수 있는 길이² − 몸통 높이²) − 지금 수평 거리   ← 리그에서 직접 잽니다
계획 보폭 = 2 × 작업 반경 × strideUsage                          ← 나머지는 가감속 여유
한 바퀴   = 계획 보폭 ÷ 속도
걸음 하나 = 한 바퀴 ÷ 묶음 수
최고 속도 = 계획 보폭 ÷ (걸음 시간 하한 × 묶음 수)
```

다리를 바꾸면 이 값이 전부 자동으로 다시 계산됩니다. **걸음 수치를 손으로 맞출 일이 없습니다.**

### 고쳐 놓은 세 가지 함정

1. **짝이 어긋난 채 굳는 것** — 걸음은 **모든 발이 땅에 있을 때만** 시작합니다. 예전에는 짝이 한 번 어긋나면 둘 중 하나가 언제나 공중에 있어 나머지 다리가 **한 걸음도 떼지 못했습니다.** (시뮬레이션에서 10초 동안 두 다리 98걸음, 나머지 0걸음)
2. **출발할 때 끌려나가는 것** — 드라이버가 `PlanForMotion` 으로 **내려는 속도**를 미리 알려 주므로 첫 걸음부터 순항 박자입니다.
3. **손으로 적은 보폭** — 예전에는 0.9m 라고 적어 두었는데 실제 다리가 감당하는 것은 0.33m 였습니다.

## 묶음 표 — 다리 수별 보행

보행은 "짝"이 아니라 **묶음 번호**로 적습니다. 그래야 다리 수가 몇이든 같은 코드로 돕니다.

| 다리 | 파도보 | 교대보 |
|---|---|---|
| 2족 | `L / R` | `L / R` |
| 3족 | `FL / FR / R` | (홀수라 파도보로 물러남) |
| 4족 | `FL / FR / BL / BR` | `{FL,BR} / {FR,BL}` 대각선 |
| 6족 | 하나씩 여섯 | `{FL,MR,BL} / {FR,ML,BR}` 삼각보 |

교대보의 묶음은 `(줄번호 + 좌우) % 2` 하나로 4족의 대각선과 6족의 삼각보가 동시에 나옵니다.

## 매 프레임 순서

```
FixedUpdate  RobotPhysicsMotor  지지 용수철 · 목표 속도 · 회전
Update       RobotDriver        목표까지의 명령을 만들어 모터에 넘김
Update       RobotKnockdown     넘어짐 단계 진행 (쓰러짐 판정 · 뜸 · 기립 보간)
LateUpdate   WalkerRobot        자세에 따라 갈라집니다 (서 있음 / 늘어짐 / 일어남)
                                1. 루트의 속도·회전율을 잰다
                                2. 발이 가고 싶은 자리를 찾는다
                                3. 어느 묶음이 나갈지 정한다  (모든 발이 땅에 있을 때만)
                                4. 발을 옮긴다        ← 마디는 아직 안 건드립니다
                                5. 몸통 자세를 잡는다
                                6. 마디를 세운다      ← 5번이 정한 자리에서 IK
```

4와 6을 나누지 않으면 마디가 **지난 프레임의 몸통**에서 풀려 발이 미세하게 떱니다.

## 지형을 못 찾을 때

**이 월드의 평지는 y≈19.6m 에 있습니다.** (터레인 높이 70m × 기준 높이 0.28)
프리팹을 원점 근처에 놓으면 **지면보다 20m 아래**입니다. 아래로 쏘는 레이는 위에 있는 표면에 닿지 않고,
터레인 콜라이더는 아래에서 올려다볼 때 잡히지 않습니다. **레이캐스트로는 원리적으로 못 찾는 자리**입니다.

그래서 `GroundProbe` 가 레이캐스트를 놓치면 **터레인 높이맵에 직접** 묻고,
`snapToGroundOnStart` 가 실행할 때 루트를 스스로 지형 위로 올립니다.

이상하면 `CarDrive > Gameplay > 보행 로봇 지면 점검` 이 레이캐스트와 높이맵을 나란히 찍어 원인을 구분해 줍니다.

> 발이 **자기 몸을 밟지 않도록** 지면 레이어를 `Ground` 와 `Prop` 으로 좁혀 두었습니다.
> 로봇 콜라이더는 `Default` 에 있으므로 탐침에 걸리지 않습니다.

| `selfCollision` | 다리가 자기 몸통과 부딪히게 할지. 리그가 겹쳐 있으면 끄세요 |
| `limpHangLength` | 힘이 풀린 다리가 매달리는 길이 (뻗을 수 있는 길이에 대한 비율) |
| `limpGravity` · `limpDamping` | 늘어진 다리의 중력과 흔들림 감쇠. 감쇠를 낮추면 오래 휘청입니다 |
| `riseLegFraction` | 일어나는 시간 중 다리를 옮기는 데 쓰는 비율. 키우면 다리가 더 여유 있게 자리를 잡습니다 |
| `riseBodyDelay` | 몸이 올라오기 시작하는 시점. 0이면 다리와 동시에, 크면 다리가 먼저 |
| `riseOrder` | 일어날 때 다리를 딛는 차례 (배선 순서 / 보행 묶음 / 낮은 발부터) |
| `riseStepShare` | 한 다리가 차지하는 시간 비율. 1=전부 동시, 작을수록 또박또박 |
| `riseLiftScale` | 일어날 때 발이 그리는 호의 높이 배율 |
| `strideUsage` | 작업 반경을 얼마나 쓸지. 1에 가까울수록 성큼성큼, 가감속 여유는 사라집니다 |
| `stepTriggerFraction` | 계획 보폭의 이만큼 벗어나면 걸음 시작. 작을수록 종종걸음 |
| `stepDuration` · `minStepDuration` | 걸음 시간의 상한·하한. **하한이 최고 속도를 정합니다** |
| `strideScale` | 다리를 얼마나 펴서 쓸지. 키우면 보폭이 늘지만 실루엣이 뻣뻣해집니다 |
| `stepHeight` | 발을 드는 높이. 스트라이더처럼 높이 들면 걸음이 눈에 들어옵니다 |
| `WalkerLeg.kneePole` | 무릎이 꺾이는 방향. **비워 두면 바깥 위(벌어진 다리), 뒤쪽을 넣으면 역관절** |
| `WalkerLeg.homeOffset` | 발이 서는 자리. 바깥으로 밀수록 작업 반경이 줄어듭니다 |
| `bodyPositionSpring.frequency` | 몸통이 발을 따라붙는 빠르기. 낮추면 무거워 보입니다 |
| `bodyBob` | 들린 발 때문에 생기는 흔들림. 2족은 크게, 3족은 작게 |
| `leanIntoTurn` · `pitchIntoAccel` | 선회·가감속에 기우는 정도. 1g 가속이면 45도 기준 |

## 몸통 높이와 다리 길이는 함께 정합니다

**이것이 이 리그에서 가장 조용히 망가지는 값입니다.** 오류도 경고도 나지 않고, 로봇은 그저
**느리게 기어가며 제자리에서 통통 튑니다.**

다리 뻗기가 R 이고 몸통이 h 높이에 서 있으면, 발이 앞뒤로 쓸 수 있는 **수평** 여유는
√(R² − h²) 입니다. 제곱근이라 h 가 R 에 가까워지는 마지막 구간에서 **절벽처럼 무너집니다.**

| h / R | 남는 수평 |
|---|---|
| 50% | 87% |
| 80% | 60% |
| 90% | 44% |
| **96%** | **28%** |

거기서 다시 고관절과 발자리 사이의 거리를 빼야 실제 작업 반경이 나옵니다.
그 뺄 값이 고정이므로, 남는 수평이 줄면 **작업 반경은 그보다 훨씬 빠르게** 사라집니다.

### 실제로 겪은 일

스트라이더의 `standHeight` 를 4.0 에서 6.2 로 올린 적이 있습니다. 다리 뻗기는 6.3m 였으니
h/R = 96% 입니다.

| | 높이 6.2 | 높이 5.2 · 다리 7.8m |
|---|---|---|
| 작업 반경 | **0.22 m** | 3.34 m |
| 보폭 | **0.26 m** | 4.00 m |
| 다리가 낼 수 있는 속도 | **0.43 m/s** | 6.67 m/s |
| 실제 속도 (순항 2.2 요청) | **0.43 m/s** | 2.20 m/s |
| 초당 걸음 | **5.0** | 1.6 |
| 걸음마다 몸통 상하 | 0.28 m | 0.14 m |

보폭이 26cm 라 **13cm 만 움직여도 걸음이 새로 시작됩니다.** 그때마다 발이 `stepHeight` 1.2m 씩
들리고 몸통이 그 평균만큼 따라 오르니, 초당 다섯 번 튀면서 0.43m/s 로 기어갔습니다.

> **왜 아무 말이 없었는가.** `RobotDriver` 는 순항 속도를 `WalkerRobot.MaxTravelSpeed` 로
> **조용히 묶습니다.** 다리가 못 따라가는 속도로 밀면 발이 끌리기 때문에 그 자체는 옳은 처리입니다.
> 문제는 그것이 **설정 실수와 구분되지 않는다**는 것이었습니다.
> 지금은 `RobotDriver.Start` 가 순항 속도가 다리 능력을 20% 넘게 웃돌면 **경고를 찍습니다.**

### 그래서 키를 키우려면

몸통을 올리는 것이 아니라 **다리를 늘립니다.** 높이만 올리면 위 표의 오른쪽 열이 왼쪽으로 갑니다.
목표 작업 반경 r 에서 필요한 다리 길이는 이렇게 나옵니다.

```
필요한 뻗기 R = √(h² + (r + 고관절→발자리 수평거리)²)
다리 길이     = R / strideScale
```

스트라이더는 h=5.2, r=3.3, 수평거리 1.55 → R = 7.0 → 다리 7.8m 입니다.

## 리그를 손으로 다듬기 — 재생하지 않고

`WalkerRobot` 은 `[ExecuteAlways]` 입니다. **재생 버튼을 누르지 않아도** 다리가 제 자세로 서 있고,
관절 하나를 끌어 옮기면 **나머지가 따라옵니다.**

| 무엇을 끌면 | 무슨 일이 일어나는가 |
|---|---|
| 고관절(`Femur`) | 다리 전체가 따라 옮겨집니다 |
| 무릎(`Tibia`) | **넓적마디 길이**가 바뀌고, 종아리마디가 새 길이로 다시 풀립니다 |
| 발목(`Tarsus`) | **종아리마디 길이**가 바뀝니다 |
| 인스펙터의 `homeOffset` | 발이 놓이는 자리가 바뀌고 다리 전체가 다시 풀립니다 |

### 작업 순서

1. `05.Prefabs/Robot/` 의 프리팹을 더블클릭해 **프리팹 모드**로 엽니다 (또는 씬에 꺼냅니다)
2. **재생 버튼은 누르지 않습니다.** `[ExecuteAlways]` 라 편집 중에도 IK 가 돕니다
3. 계층에서 마디를 골라 끕니다

```
WalkerRobot_Quadruped
└ Body
  ├ Leg_FrontLeft        ← 고관절.  끌면 다리 전체가 옮겨집니다
  │ └ Femur              ← 이걸 끌어도 같습니다 (뿌리로 접힙니다)
  │   ├ Tibia            ← 무릎.    끌면 넓적마디 길이가 바뀝니다
  │   │ └ Tarsus         ← 발목.    끌면 종아리마디 길이가 바뀝니다
```

`Femur` 는 다리 뿌리와 같은 자리에 있어 씬 뷰에서 **둘 중 아무거나 잡힙니다.** 넓적마디만
옮겨지면 좌우 대칭이 뿌리 자리를 보므로 짝이 따라오지 않고, 발자리는 루트 기준이라 다리만
혼자 밀려납니다. 그래서 넓적마디의 어긋남은 **뿌리로 접어 넣습니다.** 무엇을 끌어도 같습니다.

인스펙터로 바꿀 것: `homeOffset` (발이 놓이는 자리), `kneePole` (무릎이 꺾이는 쪽).

### 다리 하나만 고치면 나머지가 따라옵니다

다리를 넷 만들면서 같은 값을 네 번 넣는 것은 실수가 나기 쉽고, 한 번 어긋나면 걸음이 미묘하게
절뚝이는데 **눈으로는 어느 다리가 다른지 알기 어렵습니다.** 그래서 `WalkerRobot.rigSync` 가
고친 다리를 나머지에 옮깁니다.

| | 어디까지 옮기는가 |
|---|---|
| `Off` | 아무 데도. **다리마다 완전히 다르게** 만들 수 있습니다 |
| `MirrorPair` **(기본)** | **좌우 짝에게만.** 길이 + 고관절·발자리·무릎 방향을 X 대칭으로 |
| `AllLegs` | **모든 다리**의 길이를 하나로. 좌우 짝은 자리까지 대칭 |

**어느 다리를 고쳐도 됩니다.** 지난 그리기 때의 모양을 기억해 두었다가 이번에 달라진 다리를
찾고, 그것을 본으로 삼습니다. "0번 다리만 고치세요" 같은 규칙을 외울 필요가 없습니다.

좌우 짝은 **발자리가 Z 는 같고 X 는 부호만 다른** 다리입니다. 4족은 앞끼리·뒤끼리 짝이 되고,
스트라이더의 뒷다리는 가운데라 짝이 없어 그대로 남습니다.

> **여러 개가 한꺼번에 달라졌으면 손대지 않습니다.** 씬을 막 열었거나 프리팹을 다시 구운
> 직후가 그렇습니다. 그때 옮기면 일부러 만든 비대칭을 뭉개 버립니다. 기억만 새로 하고 넘어갑니다.

### 다리마다 길이를 다르게

`MirrorPair` (기본)면 **앞다리와 뒷다리를 다르게** 둘 수 있습니다. 좌우만 붙어 다니므로
앞이 짧고 뒤가 긴 짐승 같은 비례가 그대로 남습니다. 왼쪽 앞다리의 무릎을 끌면 오른쪽 앞다리만
따라오고, 뒷다리는 건드리지 않습니다.

**네 다리를 전부 다르게** 하려면 `Off` 로 두세요. 그때는 좌우 대칭도 손으로 맞춰야 합니다.

> 다리 길이가 서로 다르면 **작업 반경은 가장 짧은 다리가 정합니다.** 한 다리만 짧아도 보폭
> 전체가 그 다리에 묶입니다 — 그래야 짧은 다리가 끌려 다니지 않습니다.

### 몸통을 앞뒤로 기울이기

`WalkerRobot.standPitch` (도). 양수가 앞으로 숙인 자세입니다. 가감속 기울임과 달리
**가만히 있어도 남아 있습니다.** 앞으로 숙이면 맹수처럼, 뒤로 젖히면 버티고 선 중장비처럼 보입니다.

실루엣만 바뀌는 것이 아닙니다. 몸통이 기울면 **고관절이 앞뒤로 옮겨져** 다리마다 뻗는 여유가
달라집니다 — 앞으로 숙이면 앞다리는 좁아지고 뒷다리는 넓어집니다. 작업 반경은 리그에서 다시
재므로 그 변화가 걸음에 저절로 반영됩니다.

템플릿에 `StandPitch` 로 적으면 굽는 단계에서 반영됩니다. 마디는 몸통의 자식이라 계산이 전부
몸통 기준인데, 발자리와 위쪽 방향은 루트 기준으로 적혀 있습니다. 그래서 빌더가 그 값들을
**기운 만큼 되돌려** 넣습니다. 그러지 않으면 기운 각도만큼 발이 앞뒤로 밀립니다.

## 이동 속도와 보폭

**보폭은 직접 정하는 값이 아니라 기하에서 나옵니다.** 사슬은 이렇습니다.

```
작업 반경   ← 다리 기하 · standHeight · standPitch · strideScale
보폭       = 2 × 작업 반경 × strideUsage
한계 속도   = 보폭 ÷ (최소 걸음시간 × 묶음 수)
실제 속도   = min(cruiseSpeed, 한계 속도)          ← 드라이버가 묶습니다
걸음 시간   = clamp((보폭 ÷ 속도) ÷ 묶음 수, 최소, 최대)
```

지금 세 로봇의 값입니다.

| | 4족 | 2족 | 3족 |
|---|---|---|---|
| 작업 반경 | 0.61 m | 1.56 m | 3.34 m |
| 보폭 | 0.85 m | 1.56 m | 4.00 m |
| **한계 속도** | 4.25 m/s | 3.12 m/s | 6.67 m/s |
| 순항 (`cruiseSpeed`) | 1.60 | 1.40 | 2.20 m/s |
| 걸음 하나 | 0.27초 | 0.56초 | 0.61초 |

### 무엇을 만질 것인가

| 하고 싶은 것 | 값 | 어디 | 지금 |
|---|---|---|---|
| 더 빨리 가게 | `cruiseSpeed` | `RobotDriver` | 1.6 / 1.4 / 2.2 |
| 보폭을 넓게 | `strideUsage` (0.4~1) | `WalkerRobot` | 0.7 / 0.5 / 0.6 |
| 다리를 더 뻗게 | `strideScale` (0.3~1) | `WalkerRobot` | 0.9 전부 |
| 종종걸음으로 | `stepTriggerFraction`↓ | `WalkerRobot` | 0.5 / 0.55 / 0.5 |
| 발을 높이 들게 | `stepHeight` | `WalkerRobot` | 0.3 / 0.5 / 1.2 |
| 한 걸음을 쿵 느리게 | `stepDuration` (최대) | `WalkerRobot` | 0.28 / 0.6 / 0.7 |
| 한계 속도를 올리게 | `minStepDuration`↓ | `WalkerRobot` | 0.1 / 0.25 / 0.2 |
| 회전을 빠르게 | `turnRate` | `RobotDriver` | 130 / 90 / 55 |

**`cruiseSpeed` 를 올렸는데 안 빨라지면** 한계 속도에 막힌 것입니다. 그때는 보폭을 넓히거나
(`strideUsage`↑ · `strideScale`↑ · 다리를 길게 · `standHeight`↓) 최소 걸음시간을 줄입니다.
`RobotDriver` 가 시작할 때 경고를 찍습니다.

`strideUsage` 는 **작업 반경 중 걸음에 쓸 몫**입니다. 나머지는 가감속·선회에 남겨 두는 여유라,
1에 가깝게 밀면 방향을 틀 때 발이 반경 밖으로 밀려 끌립니다. 0.5~0.7 이 실용 범위입니다.

`stepTriggerFraction` 은 **발이 계획된 보폭의 이만큼 벗어나면 걸음을 시작**한다는 뜻입니다.
낮추면 종종걸음이 되고 발이 자주 들려 부산해 보입니다. 높이면 성큼성큼 걷지만 발이 더 끌립니다.

### 계층 구조가 유일한 진실입니다

예전에는 마디 길이를 `WalkerLeg` 에 **적어 두고** 비어 있을 때만 리그에서 쟀습니다.
그러면 관절을 끌어 옮겨도 적어 둔 숫자는 그대로라, **화면의 마디와 IK 가 믿는 길이가 어긋납니다.**
겉보기에는 멀쩡한데 재생하는 순간 다리가 다른 곳으로 갑니다 — 두 값이 서로 다른 곳에 적혀 있어
눈으로는 잡을 수 없는 종류의 어긋남입니다.

지금은 `Initialize` 가 **언제나** 리그에서 잽니다. 인스펙터의 길이 숫자는 결과를 보여 주는 창일 뿐입니다.

> **축을 벗어나게 끌면 되돌립니다.** 마디 규약은 "로컬 +Z 가 다음 관절"입니다.
> 씬 뷰에서 비스듬히 끌면 유니티는 그것을 그대로 `localPosition` 에 적는데,
> `MeasureFromRig` 는 **거리만 취하고 +Z 축 위로 되돌려** 놓습니다.
> 그래서 끌어 옮기는 것이 곧 **길이를 고치는 것**이 됩니다.

편집 중에는 **스프링을 돌리지 않고 지면도 재지 않습니다.** 2차 시스템은 시간이 지나야 목표에 닿는데
편집 중에는 시간이 흐르지 않고, 매 그리기마다 레이를 쏘면 씬이 무거워지기 때문입니다.
대신 몸통을 곧장 `standHeight` 에 놓습니다. 계산이 늘 같은 답을 내므로 가만히 두면 씬이 계속 더러워지지 않습니다.

## 스케일은 (1, 1, 1) 입니다

프리팹의 **모든 오브젝트**가 스케일 1입니다. 크기는 트랜스폼이 아니라 **메시 안에** 들어 있습니다.

| | 트랜스폼 수 | 스케일 1이 아닌 것 |
|---|---|---|
| 4족 보행기 | 43 | 0 |
| 2족 드레드노트 | 23 | 0 |
| 3족 스트라이더 | 33 | 0 |

### 왜 스케일을 걷어냈는가

예전에는 유니티 기본 도형(반지름 0.5 · 높이 2)을 가져다 `localScale` 로 눌러 마디 모양을 냈습니다.
그러면 오브젝트마다 (0.085, 0.3, 0.085) 같은 **비균등 스케일**이 남습니다. 그 자체로 틀린 것은
아니지만 위험한 상태입니다.

1. 비균등 스케일이 붙은 트랜스폼 **아래에 무언가를 달면** 그 자식이 찌그러집니다. 회전까지 섞이면 기울어진 채 늘어나 되돌릴 수 없습니다
2. 콜라이더·리지드바디가 그 아래로 들어가면 **물리 크기가 눈에 보이는 것과 달라집니다**
3. 길이를 바꾸려면 스케일을 고쳐야 하는데, 그 값이 **메시 원본 크기에 대한 비율**이라 "이 마디는 0.6m" 라는 뜻을 잃습니다

3번이 리그 편집과 정면으로 부딪힙니다. 관절을 끌어 길이를 바꾸는 작업을 하려면
길이가 **미터로 읽혀야** 하는데, 스케일은 배율이라 그렇지 않습니다.

### ProBuilder 로 실제 크기로 굽습니다

`Editor/RobotMeshLibrary.cs` 가 `ShapeGenerator` 로 상자·원기둥·구를 **그 치수 그대로** 만들어
`04.Art/02.Models/Robot/` 에 에셋으로 저장합니다. 같은 치수는 한 번만 굽고 다시 씁니다.
이름에 치수가 들어 있어 (`Limb_L0.6_D0.085`) 에셋만 봐도 무엇인지 압니다.

**축까지 구워 넣습니다.** ProBuilder 원기둥은 Y 축으로 서 있고 가운데가 원점입니다.
마디 규약은 "+Z 가 다음 관절, 원점이 관절"이므로 눕히고 미는 변환을 **정점에 미리 적용**합니다.
그래서 메시를 붙이는 오브젝트는 위치·회전·스케일이 **전부 기본값**입니다.

> 마디 길이를 바꾸려면 스케일이 아니라 **그 길이의 메시를 새로 굽습니다.**
> 템플릿 치수를 고치고 `CarDrive/Gameplay/보행 로봇/전부 만들기` 를 다시 돌리면 됩니다.

## 메시를 고치려면

고치는 층이 세 개입니다. 위로 갈수록 흔하고 쉽습니다.

### 1. 치수만 바꾸기 — 대부분 이것

`Editor/WalkerTemplates.cs` 의 숫자를 고치고 `CarDrive/Gameplay/보행 로봇/전부 만들기` 를 돌립니다.
`Femur`, `Tibia`, `Tarsus`, `Thickness`, `BodySize`, `MountSize` 가 그대로 미터입니다.
라이브러리가 새 치수의 메시를 굽고 프리팹이 그것을 씁니다.

### 2. 도형 종류 바꾸기

`Editor/RobotMeshLibrary.cs` 에 함수를 더합니다. ProBuilder 가 주는 생성기가 여럿입니다.

| 생성기 | 쓸 만한 곳 |
|---|---|
| `GeneratePrism` | 각진 마디 |
| `GeneratePipe` | 속이 빈 관 — 기계 느낌 |
| `GenerateCone` | 끝이 뾰족한 발 |
| `GenerateStair` · `GenerateArch` | 몸통 장식 |

`CylinderAlongZ` 를 본떠 쓰면 됩니다. **눕히고 미는 변환을 굽는 것**만 잊지 마세요 —
마디 메시는 "원점이 관절, +Z 가 다음 관절" 규약을 지켜야 합니다.

### 3. 손으로 깎기 — ProBuilder

1. 마디 오브젝트를 씬에 놓습니다 (프리팹을 꺼내거나, 빈 오브젝트에 메시를 걸칩니다)
2. `Tools/ProBuilder/Object/Pro Builderize` — 이제 ProBuilder 도구가 그 메시를 잡습니다
3. 원하는 대로 깎습니다
4. 그 오브젝트를 고른 채 `CarDrive/Gameplay/보행 로봇/선택한 메시를 로봇 메시로 굽기`
5. 덮어쓸 에셋을 고릅니다 (`04.Art/02.Models/Robot/`)

> **덮어쓰면 GUID 가 그대로 남습니다.** 그래서 그 메시를 쓰는 **모든 프리팹이 한 번에** 바뀝니다 —
> 프리팹을 다시 구울 필요가 없습니다. 네 다리가 같은 메시를 나눠 쓰므로 **하나만 고치면 넷이 함께** 바뀝니다.

오브젝트의 위치·회전·스케일은 **굽지 않습니다.** 규약을 지키려면 그 자리에 놓인 그대로 다듬어야 합니다.

### 이미 있는 에셋은 덮어쓰지 않습니다

라이브러리는 같은 이름의 에셋이 있으면 **그것을 그대로 씁니다.**
그래서 손으로 다듬은 메시는 `전부 만들기` 를 다시 돌려도 **살아남습니다.**

뒤집어 말하면, `CylinderSides` 같은 코드 상수를 고쳐도 기존 에셋은 그대로입니다.
다시 굽고 싶으면 `04.Art/02.Models/Robot/` 의 에셋을 **지우고** 돌리세요.

### 아예 다른 모델을 쓰려면

프리팹의 `Mesh Filter` 칸을 바꾸면 됩니다. 규약 셋만 지키면 IK 는 그대로 돕니다.

1. 마디 메시는 **원점이 관절**, **+Z 가 다음 관절**
2. 크기는 메시 안에 — 오브젝트 스케일은 **(1, 1, 1)**
3. 충돌은 메시가 맡지 않습니다 — 몸통 상자와 마디 캡슐이 따로 있습니다

## 새 형태를 추가하려면

`Editor/WalkerTemplates.cs` 에 항목을 하나 더하면 됩니다. 빌더는 고칠 필요가 없습니다.

1. 다리 순서는 **앞에서 뒤로, 각 줄마다 왼쪽 · 오른쪽** — 교대보의 대각선이 이 순서를 전제로 나옵니다
2. `KneePole` 을 비우면 바깥 위(벌어진 다리), 뒤쪽 벡터를 넣으면 역관절
3. 마디의 **로컬 +Z 가 다음 관절**을 향합니다 (메시는 자식에서 돌려 맞춥니다)
4. `Home` 은 루트 로컬이고 **Y 는 0**
5. 다리를 여섯으로 늘리면 교대보가 저절로 **삼각보**가 됩니다
6. **고관절을 몸통 콜라이더 밖에** 두세요. 안에 박히면 서 있기만 해도 파고든 상태라 자기 충돌을 켤 수 없습니다
7. 치수는 **미터로** 적으세요. 메시가 그 크기로 구워지므로 스케일을 건드릴 일이 없습니다
8. `StandHeight` 를 올릴 때는 **다리도 함께** 늘리세요. 다리 뻗기의 90% 를 넘으면 작업 반경이 절벽처럼 무너집니다

## 수학 출처

- Matched Z-transform method — 시간 간격이 커져도 연속계와 같은 속도로 감쇠하게 만드는 극점 맞추기
- Semi-implicit Euler method — 진동계에서 에너지를 벌지 않는 적분 순서
- Verlet integration — 위치로 제약을 맞추는 사슬 (`VerletChain` — 통제를 잃은 다리가 이것으로 매달립니다)
- t3ssel8r, "Giving Personality to Procedural Animations using Math"

## 적으로서의 로봇

`RobotCombatant` 를 붙이면 로봇이 **게임의 전투 규약에 걸립니다.** 프리팹 둘에는 이미 붙어 있습니다.
(붙이거나 다시 맞추려면 `CarDrive > Gameplay > 보행 로봇 > 전투 부품 붙이기`)

| 무엇 | 어떻게 |
|---|---|
| **앙크로 때리기** | `IDamageable` — `PlayerAttacker` 의 `SphereCast` 가 잡습니다 |
| **차로 들이받기** | `IHostile` — `CarCollisionHandler` 가 적으로 봅니다 |
| **발로 밟히기** | `IHostile` — `PlayerImpactReceiver` 가 적으로 봅니다 |
| **체력** | `EnemyHealth`. 질량 1kg 당 0.1 — 드레드노트 90, 스트라이더 200 |

**세 경로 모두 로봇을 위해 고친 코드가 한 줄도 없습니다.** 그것들은 이미 태그 문자열이 아니라
인터페이스로 적을 가리고 있었고, 로봇은 그 인터페이스를 달았을 뿐입니다.

**맞은 방향은 받지 않습니다.** `IDamageable.TakeDamage` 에 방향이 없기 때문입니다.
그래도 휘청임은 이미 나옵니다 — 차에 받히면 물리 충돌이 `staggerOnCollision` 을 통해
방향까지 갖고 들어옵니다. 여기서 방향을 지어내면 **물리가 이미 만든 반응과 두 번 겹칩니다.**

**죽어도 사라지지 않습니다.** 로봇은 풀에서 나오지 않았고, 쓰러진 몸은 `Limp` 자세로 계속
그려집니다. 그 자리에 남는 편이 이 게임의 세계관에 맞습니다 — 지형이 파괴되지 않고
돌아갈 마을이 남아 있는 것과 같은 이유입니다. (`stayDownOnDeath` 를 끄면 다시 일어납니다)

## 규칙은 리그 밖에 있습니다

`WalkerRobot` 은 **다리를 어디에 놓을지**만 압니다. 판단은 셋으로 나뉘어 있고, 셋 다
`Transform` 도 `WalkerLeg` 도 모르므로 **씬 없이 검증됩니다.**

| 파일 | 무엇을 정하는가 |
|---|---|
| `WalkerGait` | 다리 수와 보행에서 **묶음**을 만든다 (4족 대각선, 3족 파도보) |
| `WalkerStepPlanner` | 그 묶음 중 **다음에 어느 것이 나갈지**와 시차 예약 |
| `WalkerRiseOrdering` | 일어날 때 **딛는 차례** |

`WalkerRobot.Editor.cs` 는 `#if UNITY_EDITOR` 로 갈라 둔 partial 입니다 — 리그 편집과
기즈모 290줄이 들어 있고, **출시 빌드에는 한 줄도 들어가지 않습니다.**
