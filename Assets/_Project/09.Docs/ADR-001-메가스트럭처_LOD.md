# ADR-001: 시타델 LOD 를 데시메이션이 아니라 <b>생성</b>으로 만든다

**상태:** 채택됨 (구현 완료, 커밋 `cdf88d1`)
**날짜:** 2026-09-09
**결정 근거:** 이 저장소의 실측값. 추정으로 정한 것은 없다.

---

## 맥락

메가스트럭처의 시타델은 화면에 보이는 삼각형의 **절반 가까이**를 혼자 차지한다.

| | 삼각형 |
|---|---|
| 데크 위 시점에서 보이는 것 전부 | 51,594 |
| 그중 시타델 | 23,592 (46%) |
| 시타델 메시 전체 | 30,720 |

무게가 어디 있는지 파츠별로 쟀다. 30,720 중 **29,304(95%)가 단 둘**이다.

| 파츠 | 삼각형 | 무엇 |
|---|---|---|
| `L0` | 17,904 | 48 층짜리 갤러리 — 슬롯 기둥·층 띠·통로·난간 |
| `Stage0~2Skin` | 11,400 | 세 단의 끝면 격자 — 세로 살과 가로 띠 |
| 나머지 | 1,416 | 단 상자 · 테라스 띠 · 밑동 · 꼭대기 |

**작용하는 힘 넷:**

1. **형상이 상자뿐이다.** `hardsurface.Mass` 는 축 정렬 상자와 (사재용) 각재만 쌓는다.
   모따기도 불리언도 없다. 날카로운 각이 이 언어의 전부다.
2. **형상을 우리가 생성한다.** 블렌더 스크립트가 매번 새로 짓는다. 손으로 만든
   에셋이 아니므로 <b>다르게 지을 수 있다</b>.
3. **병목은 삼각형이 아니라 드로우 제출이다.** 스탠드얼론 프로파일에서 렌더
   스레드의 87%. 렌더러를 늘리는 선택은 그 자체로 비용이다.
4. **LODGroup 의 화면 비율이 이 크기에서 작동하지 않는다.** 유니티는
   `size / (거리 × 2·tan(화각/2))` 로 LOD 를 고르는데, 시타델의 실제 크기 505 m
   로는 파클립 482 m 에서도 0.81 이다. 임계값 최대치인 1 로 두어도 갈아탈 일이 없다.

---

## 결정

**블렌더에서 저해상도 판본을 따로 생성하고, `LODGroup.size` 로 교체 거리를 적는다.**

- `build(name, coarse=True)` 가 갤러리와 끝면 격자를 <b>빼고</b> 한 번 더 짓는다 →
  `SM_Mega_Citadel_LOD1.fbx`, **1,416 삼각형 (95% 감소)**
- `MegastructureSetup.AttachLod()` 가 원래 프리팹에 `LODGroup` 을 붙인다.
  LOD 0 = 기존 파츠 11 개, LOD 1 = 거친 메시 하나
- `size = 117` — 실제 크기가 아니라 <b>"300 m 에서 갈아탄다"를 적는 자리</b>다
  (0.30 × 300 m × 1.30). 300 m 인 이유는 안개가 257 m 에서 닫히고 이 구조물은
  그 뒤로 45% 만 남으므로(`_FogScale 0.55`), 그 밖에서 격자 한 칸(12 × 21 m)이
  화면 높이의 4% 밖에 안 되기 때문이다.

## 검토한 선택지

### A. 데시메이션 라이브러리 — `Whinarn/UnityMeshSimplifier` (MIT)

| 축 | 평가 |
|---|---|
| 복잡도 | 낮음 — 패키지 하나, API 한 줄 |
| 비용 | 라이선스 깨끗(MIT), 빌드 시간 증가 |
| 결과 품질 | **나쁨** — 상자를 깎으면 각이 뭉개진다 |
| 팀 친숙도 | 표준 도구라 널리 알려져 있음 |

**장점:** 손댈 것이 거의 없다. 어떤 메시에도 적용된다.
**단점:** 이 형상에 <b>정확히 맞지 않는 도구</b>다. 데시메이션은 곡면에서 잘
작동하고 하드서피스의 날카로운 모서리에서는 삼각형 죽을 만든다. 우리가 지운
캡슐과 남긴 격자는 전부 직각 상자다. 게다가 **생성기가 이미 구조를 알고 있는데**
그 지식을 버리고 결과물만 깎는 것은 정보를 낭비하는 것이다.

### B. 레이어별 컬링 거리 — `Camera.layerCullDistances`

| 축 | 평가 |
|---|---|
| 복잡도 | 중간 — 새 레이어 + 물리 충돌 행렬 |
| 비용 | 레이어 하나(희소 자원) |
| 결과 품질 | 좋음 — 거리로 딱 자른다 |
| 위험 | **높음** |

**장점:** 화면 비율 문제를 우회한다. 런타임 비용이 없다.
**단점:** 껍질을 새 레이어로 옮겨야 하는데 **그 껍질에 플레이어가 걸어 다니는
갤러리 콜라이더가 붙어 있다**. 레이어를 바꾸면 물리 충돌이 바뀐다
(이 프로젝트에는 이미 "Prop 레이어는 벽이 아니다" 라는 함정이 있다). 물리 행렬을
손대야 하고, 그것은 메가스트럭처 하나를 위해 프로젝트 전역 설정을 건드리는 일이다.

### C. 블렌더에서 설계된 저해상도 판본 — **채택**

| 축 | 평가 |
|---|---|
| 복잡도 | 낮음 — 생성기에 인자 하나, 유니티에 함수 하나 |
| 비용 | FBX 하나 추가(1,416 tris) |
| 결과 품질 | **좋음** — 뺄 것을 사람이 고른다 |
| 팀 친숙도 | 이 저장소의 기존 원칙과 같다 |

**장점:** 깎는 것이 아니라 **안 짓는 것**이다. 각이 살아 있고 실루엣이 유지된다.
무엇을 뺄지 생성기가 안다 — 파츠 이름으로 이미 갈라 두었기 때문이다. 외부
의존이 없다. "치수는 만든 쪽이 적고 쓰는 쪽은 읽는다" 는 이 저장소의 원칙과 같다.
**단점:** 프리셋마다 사람이 "무엇을 뺄지" 정해 줘야 한다. 자동이 아니다.

### D. 아무것도 하지 않고 먼저 프로파일한다

**장점:** 병목이 드로우 제출이라는 실측이 있는데 삼각형을 줄이는 것이
프레임에 도움이 되는지는 <b>재 보기 전에는 모른다</b>. 이 선택지는 정직하다.
**단점:** 스탠드얼론 빌드 프로파일은 별도 작업이고, 그 사이 시타델은 계속
화면 삼각형의 절반을 먹는다. 그리고 이 변경은 되돌리기 쉽다(FBX 하나와 함수 하나).

## 절충

**C 대 A 는 도구 적합성 문제다.** 데시메이션은 "메시를 받아 깎는" 도구이고,
우리에게는 메시가 아니라 **메시를 만드는 코드**가 있다. 코드가 아는 것(무엇이
갤러리이고 무엇이 덩어리인가)을 버리고 결과물만 깎으면, 알고 있던 것을 다시
추측하게 된다. 게다가 그 추측이 이 형상에서는 틀린다.

**C 대 B 는 위험 대 이득이다.** B 가 더 크게 줄일 수 있지만(멀리서 통째로 제거)
물리 설정을 건드린다. C 는 렌더러만 건드리고 콜라이더는 손대지 않는다.

**C 대 D 는 되돌릴 수 있느냐다.** 프레임 이득이 확인되지 않았다는 D 의 지적은
옳고, 이 문서는 그것을 <b>미해결로 기록한다</b>. 다만 되돌리는 비용이 파일 하나와
함수 하나이므로 먼저 넣고 나중에 재기로 한다.

## 결과

**쉬워지는 것**

- 시타델의 원거리 비용이 30,720 → 1,416 삼각형 (95%)
- 다른 프리셋에 같은 것을 붙이려면 `lod=True` 한 줄이면 된다
- 거친 판본은 파츠로 안 나누므로 원거리에서 드로우도 준다

**어려워지는 것**

- 시타델을 고칠 때 <b>두 판본이 갈라질 수 있다</b>. 같은 코드에서 나오므로
  구조는 따라오지만, "무엇을 뺄지" 는 `coarse` 분기에 손으로 적혀 있다
- `LODGroup.size` 가 실제 크기가 아니라는 것은 <b>코드를 안 읽으면 알 수 없다</b>.
  인스펙터에서 보면 틀린 값처럼 보인다

**다시 봐야 할 것**

- **프레임 이득은 아직 미확인이다.** 병목은 드로우 제출이고 이것은 삼각형을
  줄인 것이다. 스탠드얼론 프로파일을 떠서 재야 한다
- 교체 거리 300 m 는 화각 66° 를 전제한다. 화각이 바뀌면 거리도 바뀐다
- `RecalculateBounds()` 를 부르면 `size` 가 실제 크기로 덮여 교체가 사라진다.
  프리팹을 손으로 만질 때 조심해야 한다
